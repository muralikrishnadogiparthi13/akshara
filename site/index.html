Akshara अक्षर

Finding broken Indic text rendering on the web.

Every Indian consumer app ships Indic text. Almost none of it is tested, because the people doing the testing read English, and these bugs are invisible unless you read the script. A clipped shirorekha reads as the font looks a bit odd. A substituted font reads as the design looks a bit cheap. Nobody files those, and everybody sees them.

Akshara points a headless browser at a page and measures. Below is the most common finding, which is also the whole argument.

01Running it

Scanning drives a real browser, so it runs on your machine rather than in this tab. Node 20 or newer; there is nothing to sign up for. 


    

  


  
02What it looks for

  
Ordered by how often each one bites in the wild.

  

    
clipping
Ink taller than the line box, measured from the canvas ink extent and compared against Latin set in the same font.

    
fallback
The brand font has no Devanagari, so English and Hindi arrive in different faces at different weights.

    
tofu
A missing glyph — usually a webfont subset that dropped the block. Found by bitmap-matching against .notdef.

    
truncation
slice(0, 20) cutting between a consonant and its vowel sign. .length counts code units; a letter is several of them.

    
linebreak
A cluster divided across two DOM nodes. Shaping does not cross an element boundary, so the conjunct never forms.

    
normalisation
क़ exists twice in Unicode. Both spellings render identically and compare as different, so search finds one and not the other.

    
numerals
Devanagari digits sitting beside ASCII digits in one string.

    
lang
No language tag, so a screen reader reads Telugu in an English voice.

05Where a letter ends

  

    Intl.Segmenter cannot tell you. It implements UAX #29 grapheme
    clusters, and those split क्षि, which is one letter to anyone who reads it.
  


  

    
क
U+0915base

    
◌्
U+094Dvirama

    
ष
U+0937base

    
◌ि
U+093Fmark

  

  

    four code points, six code units, one letter →
    क्षि
  


  

    So Akshara segments on the orthographic unit instead. A virama binds forward into the
    consonant that follows it; every combining mark binds backward onto the cluster it
    decorates.
  

  
akshara := Base Nukta? ( Virama Join? Base Nukta? )* Mark*

  

    The trap that catches a naive implementation: every virama carries
    General_Category=Mn. Test is this a combining mark before
    is this a virama and you swallow the one character that binds the conjunct,
    and every cluster quietly splits in two.

07What it will not report

  

    A linter is worth only as much as the false positives it declines to raise.
  


  

    
A word-final virama in Tamil or Malayalam

    

      வணக்கம் and தமிழ்
      both end on a bare pulli, because that is how the language is spelled. Calling a
      trailing virama truncation would condemn two entire languages, so the rule is
      per-script: raised in Devanagari and Telugu, silent in Tamil, Malayalam and Sinhala.
    

  


  

    
A line break splitting a cluster

    

      Chrome's line breaker turns out to be shaping-aware. It wraps between letters and will
      not split an akshara even under word-break: break-all — measured, not
      assumed. Shipping a check that can never fire would be dishonest, so
      linebreak looks instead for clusters divided across DOM nodes, which is
      real, and which Chrome cannot save you from.
    

  


  
08Installing


// scan a page
npx akshara https://example.in --screenshot findings.png

// or fix the string at its source, with no browser involved
import { truncate, aksharaLength } from "akshara";

truncate("नमस्ते दोस्तों", 3);   // "नमस्ते…"  never a dangling halant
"नमस्ते".slice(0, 4);            // "नमस्"    half a letter
aksharaLength("नमस्ते");         // 3         .length says 6

  

    The exit code is non-zero when anything at or above --fail-on is found, so
    it drops straight into CI.
