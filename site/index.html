Rendering QC for Indic scripts

Your Hindi is clipped. Nobody filed a bug.

Every Indian consumer app ships Indic text. Almost none tests it, because the people testing read English and these bugs are invisible unless you read the script. Akshara points a headless browser at a page and measures.

What it finds

    
Eight ways Indic text breaks

    
Ordered by how often they bite in the wild.

    

      
clipping
Ink taller than the line box. Measured from the canvas ink extent, compared against Latin in the same font.

      
fallback
Your brand font has no Devanagari, so English and Hindi render in different faces at different weights.

      
tofu
A missing glyph — usually a webfont subset that dropped the block. Detected by bitmap-matching against .notdef.

      
truncation
slice(0,20) cuts between a consonant and its vowel sign. .length counts code units; a letter is several.

      
linebreak
A cluster split across two DOM nodes by search highlighting. Shaping doesn't cross an element boundary.

      
normalisation
क़ exists twice in Unicode. Both render identically and compare as different, so search misses one.

      
numerals
Devanagari digits beside ASCII digits in one string.

      
lang
No language tag, so a screen reader reads Telugu in an English voice.

The hard part

    
Where does a letter end?

    

      Intl.Segmenter can't tell you. It implements UAX #29 grapheme clusters,
      which split क्षि — one letter to anyone who reads it.
    


    

      
क
U+0915
base

      
◌्
U+094D
virama

      
ष
U+0937
base

      
◌ि
U+093F
mark

    

    

      4 code points · 6 UTF-16 units · reads as
      
क्षि

    


    

      So Akshara segments on the orthographic unit instead — a virama binds forward into the next
      consonant, every mark binds backward onto the cluster it decorates:
    

    
akshara := Base Nukta? ( Virama Join? Base Nukta? )* Mark*

    

      The trap that catches naive implementations: every virama carries
      General_Category=Mn, so testing “is this a combining mark” before “is this a
      virama” swallows the one character that binds the conjunct — and every cluster silently
      splits in two.

Restraint

    
Two things it refuses to report

    
A linter is only as useful as the false positives it doesn't produce.


    

      
01

      

        
Word-final viramas in Tamil and Malayalam

        

          வணக்கம் and தமிழ்
          both end on a bare pulli. That is how the language is spelled. A checker that calls a
          trailing virama “truncation” condemns two entire languages, so the rule is per-script —
          flagged in Devanagari and Telugu, silent in Tamil, Malayalam and Sinhala.
        

      

    


    

      
02

      

        
Line breaks splitting a cluster

        

          Chrome's line breaker turns out to be shaping-aware: it wraps between letters and will
          not split an akshara even under word-break: break-all. Measured, not
          assumed. Shipping a check that can never fire would be dishonest, so
          linebreak looks for clusters divided across DOM nodes instead — search-term
          highlighting, or {t.slice(0,3)}<b>{t.slice(3)}</b> — which is
          real, because shaping doesn't cross an element boundary.
        

      

    

  


  

    
Install

    
Two lines

    
# scan a page
npx akshara https://example.in --screenshot findings.png

# or fix the string bug at the source — no browser needed
import { truncate, aksharaLength } from "akshara";

truncate("नमस्ते दोस्तों", 3);  // "नमस्ते…"   never a dangling halant
"नमस्ते".slice(0, 4);           // "नमस्"     half a letter
aksharaLength("नमस्ते");        // 3          "नमस्ते".length is 6

    

      Exit code is non-zero when anything at or above --fail-on is found, so it drops
      straight into CI.
